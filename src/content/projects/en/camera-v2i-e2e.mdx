## Research question

**How does adding infrastructure-camera information change an E2E vehicle's response to a pedestrian hidden behind a parked vehicle?**

The project aims to apply this approach to a full-size vehicle. A roadside camera would observe the occluded area and send pedestrian information to the vehicle, where it would be combined with the vehicle's camera input and state. A small-scale campus platform is planned for scenario and system-function trials, including a **camera-only versus V2I-assisted E2E comparison**.

This semester focuses on research and preliminary design: quantitative requirements, interfaces, measurement boundaries, and test procedures. A separate software test measures the execution time of a candidate model architecture. Data collection, model training, and integrated vehicle trials are subsequent stages.

## Literature review and project scope

I reviewed sections of UniV2X on vehicle–infrastructure fusion and open-loop evaluation, then summarized the findings to help define the project scope. I proposed a simplified fusion approach for a planned closed-loop comparison on a small-scale vehicle.

The planned comparison asks whether earlier pedestrian information changes when the vehicle slows and how much stopping margin it retains.

The proposed interface separates **infrastructure observations** from **training targets**:

| Information | Proposed use |
| --- | --- |
| Object position, velocity, pedestrian risk, and capture time | Additional input to the V2I-assisted E2E model |
| Vehicle path overlap and braking margin | Inputs to expert rules for generating target-speed labels |
| Expert target speed and trajectory targets | Shared training targets for both models |

The pedestrian-risk feature describes the infrastructure observation. Expert labeling also considers the vehicle's path and stopping margin to specify deceleration, stopping, and restart targets.

## Pedestrian risk and target-speed labels

The preliminary design combines three elements:

- **Pedestrian state:** position relative to the curb and motion toward or away from the road.
- **Path overlap:** whether the pedestrian's occupied area intersects the vehicle's intended path.
- **Braking margin:** distance available relative to system delay, braking distance, and a safety margin.

The stopping-distance budget is expressed as `d_req = v × T_system + D_brake(v) + M`. The team plans to measure the vehicle's braking characteristics and system timing to refine these design quantities.

The expert-label plan uses this context to describe **early deceleration, a held stop while the path is occupied, and restart after the path clears**. The same target labels would be used for both E2E models.

## Stopping-based latency requirements

I examined how much delay the vehicle could tolerate while retaining the distance needed to stop. The preliminary analysis uses **30 km/h (about 8.33 m/s)** for the full-size-vehicle case and assumes constant deceleration after braking begins:

`T_total ≤ (D − v² / (2a) − g) / v`

Here, `D` is the distance from the vehicle's front to the collision-zone boundary at image capture, `a` is the assumed deceleration, and `g` is the required stopping clearance. The analysis compares decelerations of 1.5, 2.5, and 3.5 m/s² using literature as a design reference. The table uses **1.5 m/s²** and a **2 m candidate stopping clearance**.

| Available distance D | Calculated upper bound on total latency |
| --- | --- |
| 30 m | About 582 ms |
| 35 m | About 1,182 ms |

These are conditional time budgets. The final latency target will depend on the selected vehicle's braking characteristics and the observation distance available in the scenario. The campus platform has its own operating and braking conditions.

I defined total latency from **image capture to physical deceleration onset**, with the following measurement boundaries:

| Interval | Measurement boundary |
| --- | --- |
| Infrastructure | Capture (`t0`) to completed pedestrian state (`t1`) |
| Communication | Completed state (`t1`) to full message reception at the vehicle (`t2`) |
| Vehicle | Full reception (`t2`) to physical deceleration onset (`t4`) |
| Brake actuation | Applied control command (`t3`) to physical deceleration onset (`t4`), within the vehicle interval |
| Total | Capture (`t0`) to physical deceleration onset (`t4`) |

This boundary definition accounts for brake actuation once in the delay budget, followed by the braking distance after deceleration begins. The measurement plan records processing, delivery, decision, and actuation stages separately.

## Candidate-model runtime measurement

I used ChatGPT to prepare the runtime test and ran it myself to examine the compute time of **OpenDriveLab's TCP (Trajectory-guided Control Prediction)** as a vehicle E2E model candidate.

| Item | Measurement condition or result |
| --- | --- |
| Model weights | Random initialization |
| Hardware and precision | NVIDIA GeForce RTX 5070 Laptop GPU, FP32 |
| Software | Windows, Python 3.11.9, PyTorch 2.11.0+cu128 |
| Inputs | Image tensor `1×3×256×900`; state tensor `1×9` |
| Repetitions | 50 warm-up runs, followed by 600 measured runs |
| Scope | Prepared CPU inputs → GPU transfer → model forward and action calculation → CPU output values |
| Mean / median | 20.04 / 20.02 ms |
| P95 / maximum | 21.88 / 24.65 ms |

This is an execution-time measurement of a candidate architecture with random weights. Camera acquisition, image preprocessing, V2I fusion, scheduling, vehicle delivery, and physical actuation belong to later pipeline measurements. TCP remains a model candidate; driving quality and the paired-model comparison are subjects of subsequent evaluation.

## Infrastructure geometry and time alignment

The preliminary spatial design uses homography to map an image observation onto the ground plane. A common local ENU frame would connect the pedestrian estimate with vehicle position, followed by a conversion into the vehicle's frame.

The timing plan preserves the image's capture timestamp and separates **clock synchronization** from **motion compensation**. Processing, sending, receiving, fusion, and control timestamps would support later analysis of delay and message freshness.

Camera placement, ground reference points, independent accuracy checks, and timestamp conventions are subjects of the current design work.

## Planned E2E comparison

| Element | Camera-only baseline | V2I-assisted proposal |
| --- | --- | --- |
| Inputs | Vehicle camera and vehicle state | Vehicle camera, vehicle state, and infrastructure pedestrian information |
| Outputs | Waypoints and target speed | Waypoints and target speed |
| Data source | The same recorded runs | The same recorded runs |
| Training targets | Shared trajectory and expert target-speed labels | The same labels |
| Controlled conditions | Same platform, operating conditions, and low-level controller | The same conditions |

The data plan records vehicle imagery and state together with infrastructure observations during the same run. Training, validation, and test sets would be separated by **run or session**. Planned scenarios include pedestrian absence, standing inside or outside the vehicle path, approach, crossing, and departure.

The campus plan uses the small-scale platform for straight-line deceleration and stopping trials, with 8 km/h under consideration as an operating condition. Scenes would be paired and test order alternated while checking that the base model, training, and controller conditions remain comparable.

Evaluation would record event latency (P50, P95, and maximum), position bias and RMSE, deceleration onset, final stopping clearance, unnecessary deceleration, required deceleration that does not occur, contact, and safety interventions. Communication measurements cover message loss, consecutive reception gaps, recovery, model-switching delay, and command continuity.

The sampling unit is an independent run or event. Latency distributions would cover events where the required deceleration occurs; events without that response would be counted separately. Repetition counts and acceptance thresholds are part of the next design decisions. This keeps the response-time distribution separate from the rate of successful responses.

## V2I communication research

I am investigating direct UDP messaging and ROS 2/DDS over Wi-Fi as communication options between the infrastructure and vehicle computers. I am examining initial connection, how soon observations reach the vehicle, and reception continuity as the vehicle approaches the pedestrian scenario.

Current comparison criteria include:

- **Message freshness:** the time from observation to use.
- **Delivery latency:** the time from sending to reception.
- **Reception continuity:** gaps, missed or out-of-order messages, and reconnection behavior.

A dedicated Wi-Fi network and alternative connection arrangements are candidates for team discussion. The proposed fallback uses camera-only E2E while infrastructure information is unavailable or invalid and returns to the cooperative model after valid reception is restored. Model-switching delay and command continuity are planned evaluation items. The communication approach is being selected within the current **research and design phase**.

## Next design work

The next steps are to select the communication approach, refine the pedestrian-state interface, assess camera visibility and spatial alignment on site, and measure the platform's braking characteristics and pipeline timing. Those observations will inform latency targets and acceptance thresholds. Data collection, model training, and the small-scale closed-loop comparison follow this design work.
