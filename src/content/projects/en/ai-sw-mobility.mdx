## Engineering question

How can a perceived cone corridor become a trackable path and a reliable stop command when perception and vehicle feedback arrive at different times? My work connects the AEB path and stop logic with constrained steering and integration tests.

## AEB and steering design

| Design choice | Purpose | Implementation evidence |
| --- | --- | --- |
| Cone-boundary center path | Turn corridor geometry into a tracking target | AEB path generation and tracking |
| Red-entry stop latch | Preserve the stop decision after the vehicle reaches the gate | Confirmed red-pair handling and latched braking state |
| Steering and steering-rate limits | Bound command magnitude and abrupt changes | Stanley tracking and command limiting |
| Stale-input checks | Request a stop when required path or state data is unavailable | Offline AEB tests and fail-safe branches |

The [AEB implementation and tests](https://github.com/steveandy-sudo/ai-sw-mobility-portfolio) expose behavior at these boundaries. Motion preview was also implemented as part of the path-tracking work. Its effect on vehicle tracking needs to be evaluated together with the corrected steering response.

## Next experiment: steering response

The next comparison will keep the route, speed, controller settings, and input conditions fixed while recording steering response with the control-side correction. A matched earlier recording is needed for a before/after comparison.

| Record | Question it answers |
| --- | --- |
| Time-aligned target and measured steering | Does the actuator follow the requested angle, and with what delay? |
| Target path and vehicle trajectory | How large are lateral tracking errors along the route? |
| Braking request, measured speed, and stop position | Does the vehicle stop at the intended location? |
| Trial count and individual outcomes | Does the behavior repeat under the same conditions? |

Path-error summaries and stop outcomes will be reported with the operating conditions after the integrated trial.
